## Общий сведения. Партицирование

Партицирование — это логическое разделение одной большой таблицы на несколько частей (партиций), которые хранятся отдельно, но работают как одна таблица.

Причина,Польза:
- 🔍 Ускорение запросов,СУБД читает только нужные партиции (partition pruning)
- 🗑️ Удаление старых данных,Можно быстро удалить целую партицию (DROP PARTITION)
- 💾 Управление диском,Разные партиции — на разных дисках
- 🚀 Производительность,Меньше данных на сканирование

### Типы партицирования в MySQL

Тип,Описание,Пример:
- RANGE,По диапазону значений,"По годам, ID"
- LIST,По списку значений,"По регионам, статусам"
- HASH,По хэшу ключа,Равномерное распределение
- KEY,"По хэшу, поддерживаемый MySQL","Как HASH, но для любых типов (включая BLOB)"
- COLUMNS,Позволяет партицировать по нескольким столбцам,"PARTITION BY RANGE COLUMNS(a, b)"
- SUBPARTITIONING,Партиции делятся на подпартиции,Например: RANGE + HASH


### Пример: RANGE-партицирование по году
```sql
CREATE TABLE sales (
                       id INT,
                       amount DECIMAL(10,2),
                       sale_date DATE
)
    PARTITION BY RANGE (YEAR(sale_date)) (
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

При выполнении:
- MySQL создает одну логическую таблицу sales.

Физически:
- Создаются отдельные файлы/сегменты для каждой партиции.
- В InnoDB: каждый PARTITION → свой .ibd файл (например, sales#p2022.ibd, sales#p2023.ibd и т.д.).

Но в каталоге таблиц вы не увидите отдельных таблиц p2022, p2023 — они не являются таблицами.

Как работает:
- Все записи с sale_date в 2023 году → попадают в p2023.
- При запросе:
```sql
SELECT * FROM sales WHERE sale_date BETWEEN '2023-01-01' AND '2023-12-31';
```
MySQL читает только партицию p2023 → быстрее!

При необходимости можно обратиться к самой партиции. Но можно только select/delete, insert/update не работает (запрещено) 
```sql
SELECT * FROM table PARTITION (partition_name);
```

### Использовать партицирование, когда:
1. Таблица очень большая
   → > 10–100 млн строк, медленные запросы.
2. Данные логически делятся по диапазону
   → По дате (sales, logs, events), ID, региону.
3. Часто фильтруете по одному полю
   → WHERE created_at > '2023-01-01' → читается только одна партиция.
4. Нужно быстро удалять старые данные
   → ALTER TABLE ... DROP PARTITION — почти мгновенно (вместо DELETE).
5. Хотите ускорить запросы без изменения кода
   → Приложение видит одну таблицу, а СУБД читает только нужные партиции (partition pruning).

## Общий сведения. Шардирование

Разделение одной большой таблицы/базы на несколько частей (шардов), которые хранятся на разных серверах.

Оно решает проблему роста, но вводит огромную сложность: нет JOIN, сложно с транзакциями, сложно управлять.

Поэтому его не делают с самого начала — сначала используют более простые методы: индексы, репликацию, партицирование.

Шардирование применяют, только когда один сервер физически не справляется.

Шардирование можно настроить силами приложения, обращаться в нужной таблице и БД в зависимости от входного значения, 
используя свой собственный менеджер подключений/шардирования

Можно настроить средствами СУБД, правда не все поддерживают:
- MySQL — нет (из коробки)
- PostgreSQL — через расширения (например, Citus)
- Другие СУБД — да: MongoDB, CockroachDB, YugabyteDB и др.

## Заключение

### Простая аналогия
- Партицирование — как одна книга, разделённая на главы.
Вы можете открыть только нужную главу, но книга — одна.
- Шардирование — как серия книг, где каждая книга — отдельный том.
Томы стоят на разных полках (серверах), и чтобы собрать всю историю — нужно ходить по всем.

### Общая архитектура оптимизации

```sql
1. Оптимизация запросов и индексов
   ↓
2. Вертикальное масштабирование (лучше сервер)
   ↓
3. Репликация (чтение с реплик)
   ↓
4. Партицирование (по дате, ID)
   ↓
5. Шардирование (только при необходимости)
```
